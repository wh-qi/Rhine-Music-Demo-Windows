# 纯原生能提升性能吗？—— 用项目自己的实测数据回答

> 结论先说：**对帧率几乎不能。** 瓶颈是 GPU 像素填充与多 pass 后处理，这部分工作在原生里**一模一样**。
> 原生真正能买到的是：**内存、功耗/风扇、启动、以及音频输出的正确性** —— 不是 FPS。
> 数据来源：`docs/media/v0.4.0/startup/final-build.json`、`verification/PERFORMANCE-ARCHITECTURE.md`、`docs/STARTUP-V0.4.0.md`。

---

## 一、决定性的三个数字

项目自己记录了 240 帧的稳态采样（`final-build.json`）：

```json
"timing": { "samples":240, "fps":60, "frameP50":16.7, "frameP95":16.8,
            "frameMax":18.6, "over50ms":0, "cpuP95":3.3 }
"stats":  { "drawCalls":37, "triangles":1574401 }
```

| 数字 | 含义 |
| --- | --- |
| `frameP50 = 16.7 ms` | 60 Hz 垂直同步预算的**满帧**，即已经跑满 |
| `cpuP95 = 3.3 ms` | **CPU 提交只占 16.7 ms 预算的 19.8%** —— 剩下 **~80% 是纯 GPU 时间** |
| `drawCalls = 37` | 已经用 InstancedMesh 批处理好了，原生「draw call 更便宜」的优势在这里≈0 |
| `over50ms = 0` | 稳态零长帧，没有 GC 卡顿 |
| `fps = 60` | 已经到顶 |

**关键推论**：

> 原生能消灭的是那 **3.3 ms 的 CPU 提交**。但即使把它**完全变成 0**（不可能），
> 剩下的 GPU 工作仍需 ~13.4 ms，帧时间还是 16.7 ms，**FPS 一个点都不会涨**。
> 因为在 60 Hz 下，GPU 13.4 ms < 16.7 ms 预算，**帧率由垂直同步决定，不由 CPU 决定**。

**这就是答案：正处在「GPU 受限 + vsync 封顶」的状态，纯原生买不到帧率。**

## 二、逐项拆解：原生能改什么、不能改什么

| 成本项 | 现状 | 纯原生能改善吗 |
| --- | --- | --- |
| **GPU 像素填充** | 高画质缓冲约 **702 万像素**（3225×2177），另有 SSAO 全缓冲、Bokeh 深度、2048² 阴影、玻璃透射、SMAA | ❌ **完全一样**。同样的 GPU、同样的像素、同样的采样数 |
| **后处理 pass** | RenderPass + SSAO(含法线 pass) + Bokeh(含深度 pass) + SMAA + 透射背景捕获 | 🟡 **只有重写管线才行**，见第四节 |
| **三角形提交** | 157 万（理论全遍历 259 万） | 🟡 原生每次 draw 开销更低，但只有 37 次 draw → 收益微小 |
| **CPU 提交（JS + Three.js + ANGLE 翻译）** | **3.3 ms**（p95） | ✅ 可省，但被 vsync 吃掉 → **FPS 不变** |
| **GC 停顿** | `over50ms = 0`，p95 16.8 / max 18.6 | ✅ 原生无 GC，但**你现在没有这个问题** |
| **内存** | 自身上限：图集 **108 MiB** + 缓存 12 MiB + 17 纹理 + 7 几何；Electron 另加 ~250 MB Chromium 基线 | ✅ **真实收益：省掉 ~200–250 MB**，但省的是 Chromium，不是 JavaScript |
| **冷启动** | 准备 **823 ms**（`final-lifecycle-build` 849 ms） | 🟡 **部分**。其中 **432 格 / 108 MiB 封面上传（7 批）与 30 个 shader 编译**，原生同样要做 |
| **高刷屏余量** | 60 Hz 下已封顶 | ❌ 144 Hz 预算 6.9 ms，而 GPU 就要 ~13.4 ms → **原生也到不了 144** |
| **音频输出** | Chromium/WebView2 → WASAPI **共享模式**，系统重采样 | ✅✅ **唯一质变项**：独占 WASAPI / bit-perfect / 原生 DSD。但这是**正确性**，不是性能 |

## 三、项目自己的结论（很重要）

`verification/PERFORMANCE-ARCHITECTURE.md` 在 2026-09-09 就写过：

> 「结论：**GPU 几何、多 pass 与长期持续绘制是优先验证的瓶颈假设。当前没有证据表明 TypeScript 执行速度是主要瓶颈，也没有证据证明更换宿主能自动提升特定倍数的 FPS。**」

> 「**不要仅根据框架名称进行全量重写。**」

同一份文档对候选技术栈的评估也很克制：

| 方案 | 该文档的判断 |
| --- | --- |
| Electron + Three.js | 复用现有代码最直接；**不能解决既有 GPU 渲染成本** |
| Tauri 2 + Rust | 减少自带浏览器发行负担，**不代表运行内存或 FPS 必然优于 Electron** |
| Windows 原生 UI + Direct3D / Rust + wgpu | 控制力最多；**需要自行搭建材质、后处理、文本与输入系统**；开发与视觉验证成本最高，**并无本项目跑分证明其收益** |

> 注意最后一句：**这个项目已经做过这个判断了，而且结论就是「没有证据证明原生更快」。**

## 四、原生唯一真正的性能机会：重写渲染管线（不是换语言）

纯原生**不会**因为「JS 慢」而更快，但**可能**因为「你能控制管线」而更快。区别在这里：

**当前 Three.js 后处理链的碎片化成本**（文档已证实其中一部分）：
- `RenderPass` 画一遍场景
- `SSAOPass` **额外再画一遍法线**
- `BokehPass` **额外再画一遍深度**
- 阴影原本一帧生成三次 → 项目已修成 `shadowMap.autoUpdate=false` + 每帧一次
- 透射有独立的背景捕获与纹理处理

**原生能做的整合**（这才是原生性能的真正来源）：
1. **单一深度预 pass + G-Buffer**，AO / DoF / 法线 / 透射全部从同一份 G-Buffer 读取 → 省掉 2 次全场景重绘
2. **Compute Shader 合并后处理**，一次 dispatch 完成 AO+DoF+色调映射
3. **压缩纹理**：108 MiB 图集改用 BC7（约 1/4 显存与带宽）
4. **真正的分块剔除**：见下节
5. **预编译管线状态对象**，消除首次 shader 编译抖动

> ⚠️ 但请注意：**上面 1、2 两项在 Three.js 里也能部分实现**（自定义 Pass 合并、`WebGLRenderer` 的 `WebGLRenderTarget` 复用），成本远低于重写整个应用。而 3、4 两项与语言完全无关。

## 五、真正能让它更快、且便宜得多的做法

按性价比排序（全部不需要原生重写）：

| # | 优化 | 依据 | 预期 |
| --- | --- | --- | --- |
| 1 | **用「性能」画质档** | `render-quality.ts` 已内置：`pixelRatio 1` + `scale 80` → **0.72 M 像素**（vs 高画质 7.02 M，**约 1/9.7**），且 `aoSamples: 0`、`depthOfField: 0`、SMAA 关、阴影 2048→1024、透射 1→0.5 | **像素成本降 ~90%** |
| 2 | **用「原始」画质档** | `pixelRatio 1.5` → 2.53 M 像素，保留玻璃/阴影/AO/景深 | **像素成本降 64%** |
| 3 | **修 `frustumCulled = false`** | `scene.ts:404` 所有阵列 InstancedMesh 都关闭了视锥剔除 → 外围与雾中的卡片仍全量提交 | 减少三角形提交 |
| 4 | **背景 LOD** | `Ivory_Edges` 占阵列几何三角形 **69.5%**（8988/组），是背景边框 | 可砍掉约 2/3 阵列三角形 |
| 5 | **图集压缩纹理 BC7** | 108 MiB RGBA 图集 → 约 27 MiB | 显存与上传带宽 -75% |
| 6 | **不可见时停渲染** | `music-app.ts` 仍是连续 RAF | 隐藏/最小化时省电 |
| 7 | **管线整合**（见第四节 1、2） | SSAO/Bokeh 各自重绘全场景 | 可能省 2 次全场景重绘 |

> **对比一下**：第 1 项（已经内置，点一下设置就有）能砍掉 ~90% 像素成本；
> 而纯原生重写（150–300 人日）在**同样的画质档位下**砍不掉一个像素。
> 换句话说：**先把已有的画质开关用起来，再考虑第 3–7 项，最后才轮到原生。**

## 六、什么情况下纯原生才真的值

| 场景 | 原生是否有意义 |
| --- | --- |
| 你现在的规模（96–432 张封面、60 Hz 屏） | ❌ **毫无意义**，已经 60 FPS / 零长帧 |
| 你要 144 Hz 高刷屏满帧 | 🟡 需要「原生 + 管线重写」双管齐下，单换语言不够 |
| 你要跑 1000+ 专辑、更高密度 | 🟡 有意义，但先做第 3、4 项剔除与 LOD |
| 你的痛点是**内存占用 / 风扇噪音 / 笔记本续航** | ✅ **原生最实在的收益**（省 ~200–250 MB + 省 ANGLE/合成开销） |
| 你的痛点是**启动慢** | ✅ 有意义，但 823 ms 里的大头（108 MiB 上传 + shader 编译）原生也要付 |
| 你的痛点是**音质 / 独占输出 / bit-perfect** | ✅✅ **必须原生**，而且只要写一个 WAV+WASAPI 播放器（8–15 人日），**不需要重写应用** |
| 你的目标是**摆脱 Web 技术栈** | 那是工程偏好问题，不是性能问题 |

## 七、一句话总结

**纯原生换不来帧率。** 实测 `cpuP95 = 3.3 ms` 而帧预算 `16.7 ms`、`drawCalls = 37`、`over50ms = 0`、`fps = 60`——
CPU 只占两成，瓶颈在 GPU 的后处理像素成本，原生在同样的画质档位下要付**一样的 GPU 代价**。

原生真正值钱的是三件事：**内存（省 ~250 MB Chromium）、功耗、以及音频输出的正确性（独占 WASAPI/bit-perfect）**——
而这三件事里，前两件用 WebView2 外壳就能拿到一大半，第三件只需要写一个 8–15 人日的 **WAV+WASAPI 小桥**，完全不必重写那 700 KB TypeScript + 130 KB CSS。

**如果目标是"更快"，先做第五节第 1–2 项（点一下设置，像素成本降 64%~90%）；如果目标是"音质"，做第 3 项（原生音频桥）；如果目标是"内存/续航"，换 WebView2 外壳。三者加起来的工作量，仍远小于纯原生重写。**
