# Rhine Music for Windows · 音质支持方案

> 结论先说：**Windows 版在输出模式、采样率跟随、bit-perfect 三个维度可以超过 macOS 主线**——
> 因为 macOS 主线用的是 CoreAudio **共享模式**，README 明确写「不承诺独占输出、自动切换硬件采样率或 bit-perfect」。
> 本文给出完整链路分析、四档音质阶梯、实现要点与客观验收方法。

---

## 一、先把基线钉死：macOS 主线交付了什么

README 原文（`## 格式与播放边界`）：

> 「Mac 原生输出使用 **CoreAudio 共享模式**；浏览器与系统输出可能重采样。PCM 缓存格式不等于硬件实际输出格式，**本版不承诺独占输出、自动切换硬件采样率或 bit-perfect**。」

> 「此版本**不提供 Native DSD 或 DoP**，DST 压缩 DFF 尚未验证。」

代码侧印证（`native/RhineAudio.swift:71`）：

```swift
let format = AVAudioFormat(standardFormatWithSampleRate: file.processingFormat.sampleRate,
                           channels: max(2, file.processingFormat.channelCount))!
engine.connect(node, to: engine.mainMixerNode, format: format)
```

**`AVAudioFormat(standardFormatWithSampleRate:channels:)` 就是「标准格式」= 32-bit float 非交错。**
也就是说：**macOS 主线的整数 PCM 在进入引擎时已经被转成 Float32，再走共享混音器，还可能被系统重采样到设备混音采样率（通常 48 kHz）。**

> ✅ **这给了 Windows 版明确的超越空间**：独占模式可以直接把整数 PCM 按**原生采样率 + 原生位深**送到 DAC，不经过 float 转换、不经过混音器、不经过重采样。

## 二、完整链路与七个损耗点

```
源文件 → ffprobe 探测 → FFmpeg 解码 → PCM WAV 缓存 → 原生引擎 → 系统混音器 → DAC
```

| # | 环节 | 代码现状 | macOS 主线 | Windows（仅 Web Audio） | 可修 |
| --- | --- | --- | --- | --- | --- |
| 1 | **解码** | FFmpeg，`-map 0:a:0`，无 DSP、无 EQ | ✅ 无损 | ✅ 同 | 已很好 |
| 2 | **缓存位深保持** | `bits>24?s32 : bits>16?s24 : s16`，float→f32 | ✅ 保位深 | ✅ 同 | 已很好 |
| 3 | **抖动** | **全链路无任何 dither**（已核查） | ❌ 无 | ❌ 无 | 🟡 可加 |
| 4 | **引擎内部格式** | — | ⚠️ **转 Float32** | ⚠️ Chromium 也是 float | 🔴 **独占可绕过** |
| 5 | **音量** | `player.volume` float 域衰减 | float 衰减 | float 衰减 | 🟡 bit-perfect 需 unity |
| 6 | **系统混音** | — | ⚠️ **CoreAudio 共享** | ⚠️ **WASAPI 共享** | 🔴 **独占可绕过** |
| 7 | **采样率** | 缓存保原生率 | ⚠️ **跟设备混音格式，可能重采样** | ⚠️ 同 | 🔴 **独占可原生跟随** |
| 8 | **重采样器** | `aresample=...:resampler=swr:filter_size=64`（**非 libsoxr**） | swr | swr | 🟡 可换 libsoxr |
| 9 | **DSD** | 一律转 **24bit/176.4kHz PCM**（`DSD_PCM_RATE=176400`） | 转 PCM | 转 PCM | 🟡 可选 DoP |

**红点三项（4/6/7）正是共享模式的固有损失，也正是独占模式能一次全部解决的地方。**

## 三、四档音质阶梯

| 档 | 名称 | 链路 | 能力 | 相对 macOS |
| --- | --- | --- | --- | --- |
| **Q0** | 浏览器/内嵌引擎 Web Audio | Chromium → WASAPI 共享 | 有设备选择，但重采样 + 混音 | 略低 |
| **Q1** | WASAPI 共享 + 原生设备选择 | 独占桥，共享模式 | 设备选择、按设备混音格式 | **对齐** |
| **Q2** | **WASAPI 独占 + 原生采样率** | 独占桥，逐曲协商 | **不重采样、无混音、无 APO** | ✅ **超过** |
| **Q3** | **独占 + 位深匹配 + unity gain** | 全链路零转换 | **bit-perfect** | ✅✅ **远超** |
| Q3+ | 追加 DoP（可选） | DSD 原生输出 | 真 DSD | ✅✅✅ |

## 四、最终方案交付：Q3 为默认，Q1 可切

### 4.1 默认策略

**默认 Q2/Q3（独占 + 原生采样率）** —— 因为本次定调是**效果优先**，且产品定位就是「私人音乐终端 / 沉浸式聆听」。

但必须**自动回退**，不能让用户遇到「没声音」：

```
IsFormatSupported(EXCLUSIVE, 逐曲原生格式)
├─ S_OK            → 独占，原生采样率 + 原生位深
├─ 不支持该格式     → 尝试设备支持的最接近采样率（FFmpeg 用 libsoxr 重采样）
├─ DEVICE_IN_USE   → 回退共享，UI 说明「设备被其他程序独占」
├─ EXCLUSIVE_MODE_NOT_ALLOWED → 回退共享，UI 提示去「声音设置 → 设备属性 → 高级」勾选
│                     「允许应用程序独占控制该设备」
└─ 其它失败         → 回退共享，UI 显示原因
```

设置里提供 **共享 / 独占** 开关，默认独占。

### 4.2 采样率跟随（最大的单项收益）

WAV 缓存的元数据里**已经有真实的 `sampleRate`**（`music-audio.mjs:175` 写入 `metadata`），桥可以直接读：

- 44.1 kHz 的 FLAC → 设备锁定 **44.1 kHz**，而不是被 Windows 混音器重采样到 48 kHz
- 96/192 kHz 的 Hi-Res → 同样原生输出
- 切换不同采样率的曲目 → 重建 `IAudioClient`（**保留播放位置**，复用 `setDevice` 的语义）

> **这就是「自动切换硬件采样率」，macOS 主线明确不承诺的能力。**

### 4.3 位深匹配

缓存已经保位深（s16/s24/s32/f32），WASAPI 独占支持全部四种：

| 缓存 | WASAPI 格式 |
| --- | --- |
| `pcm_s16le` | 16-bit PCM |
| `pcm_s24le` | 24-bit（`WAVEFORMATEXTENSIBLE` + `wValidBitsPerSample=24`，32-bit 容器） |
| `pcm_s32le` | 32-bit PCM |
| `pcm_f32le` | 32-bit float（`WAVE_FORMAT_IEEE_FLOAT`） |

**零位深转换。**

### 4.4 bit-perfect 模式（必须诚实说明的前提）

真正的 bit-perfect 需要**同时**满足：

| 条件 | 方案中的状态 |
| --- | --- |
| 独占模式 | ✅ |
| 原生采样率 | ✅ |
| 位深匹配，无转换 | ✅ |
| 链路上无 DSP | ✅ 代码里本来就没有（`-map 0:a:0`，无 EQ/无归一化） |
| **音量为 unity gain（0 dB）** | ⚠️ **与软件音量控制天然冲突** |

> ⚠️ **关键诚实点**：`desiredVolume` 是在 float 域做衰减的。**只要音量不是 100%，就不是 bit-perfect。**
> 这不是缺陷，而是物理必然——数字音量衰减就是重写样本。foobar2000 / JRiver 的处理方式也一样。

**方案**：设置里给一个 **「bit-perfect 模式」**开关：
- 打开后应用内音量锁定 100%，UI 明确提示「请使用功放/DAC 或系统硬件音量调节」
- 关闭则恢复正常软件音量（仍然是 Q2 级，极高质量，只是不叫 bit-perfect）
- 界面上**如实标注当前处于哪一档**，不夸大

### 4.5 抖动（Dither）

现状：**全链路无抖动**（已核查，`music-audio.mjs` 里没有任何 dither）。

- Q3 位深匹配 + unity gain 时：**不需要抖动**（本来就 bit-perfect）
- 若发生衰减或位深下降：加 **TPDF 抖动 + 可选噪声整形**
- 建议做成「仅在必要时启用」，避免无谓处理

### 4.6 重采样器质量

现状用 FFmpeg `swr`（`filter_size=64`），代码注释说明「不依赖可选的 libsoxr」。

- Q2/Q3 独占 + 原生率 → **通常不需要重采样**，这是最好的结果
- 设备只支持 48 kHz 等受限场景 → **换 libsoxr**（SoX 重采样器，质量优于 swr）
- 我们本来就要自建 FFmpeg，**加 `--enable-libsoxr` 几乎没有额外成本**

### 4.7 DSD（可选的真正升级）

现状：DSD 一律转 **24bit/176.4kHz PCM**（有损于「原生 DSD」这个诉求）。

**DoP（DSD over PCM）**：把 DSD 比特流按 16 bit/样本塞进 24-bit/176.4 kHz 的 PCM 帧，用交替的 `0x05`/`0xFA` 标记填充高 8 位，经 **WASAPI 独占**送给支持 DoP 的 DAC → **DAC 解码出真正的 DSD**。

- 前提：独占模式 + 精确 176.4 kHz + DAC 支持 DoP
- 实现：需要绕过 WAV 缓存，直接读 DSF/DFF 并重新打包帧
- 成本：**P3 之后的可选阶段**（约 5–8 人日）
- 建议：作为**进阶开关**，默认仍是转 PCM（兼容性最好）

> **Native ASIO DSD** 需要 ASIO 驱动且设备相关，不建议做。

### 4.8 排除 Windows 侧干扰

- 独占模式**天然绕过**：Windows 混音器、APO 音效增强、响度均衡、空间音效
- 共享模式下这些仍会介入 → UI 给出提示（设备属性 → 高级 →「音频增强」关闭）
- 独占还需用户在系统里勾选「允许应用程序独占控制该设备」，未勾选时要**明确提示**而不是静默失败

## 五、设置界面（效果优先的加分项）

在现有「设置 → 音频输出」里扩展：

| 项 | 内容 |
| --- | --- |
| **输出模式** | 共享 / **独占**（默认独占） |
| **bit-perfect 模式** | 开关；开启时锁定音量 100% 并说明原因 |
| **设备选择** | 已有能力，保留 |
| **当前实际输出** | ⭐ **实时显示**：`44.1 kHz / 24-bit / 独占 / 无重采样` |
| **DSD 处理** | 转 PCM（默认）/ DoP（进阶，标注 DAC 需支持） |
| **回退原因** | 独占失败时明确显示原因（被占用 / 格式不支持 / 系统未允许） |

### ⭐ 信号路径显示（强烈建议）

参照 Roon / JRiver 的做法，显示**这一首正在走的真实链路**：

```
FLAC 96kHz/24bit  → [FFmpeg 解码，无重采样]  →  PCM 96/24  →  [WASAPI 独占 96/24]  →  DAC
```

这对发烧友的价值极高——**能把「实际发生了什么」变成可见、可验证的事实**，而不是靠营销话术。
数据来源现成：`/api/audio/capabilities` 已经在返回 `mode`、`devices`、`formats` 等字段，扩展即可。

## 六、客观验收方法（不靠主观听感）

| 项 | 方法 |
| --- | --- |
| **真 bit-perfect** | 播放已知测试信号（1 kHz 正弦 / 特殊比特图案），经 **VB-Cable 或硬件环回**录音，**逐比特比对**输入输出 |
| **无重采样** | 播放 44.1 kHz 文件时，确认设备处于 44.1 kHz（而非 48 kHz）；独占模式下用 `IsFormatSupported` 与实测双确认 |
| **位深匹配** | 检查 `WAVEFORMATEXTENSIBLE.wValidBitsPerSample` 与缓存位深一致 |
| **无缝接缝** | 录制过渡处波形，检查**无样本丢失、无重复、无爆音**；对照仓库既有约定「必须用音频时钟连续排程」 |
| **无声泄漏** | 播放静音段，确认底噪未被额外处理引入 |
| **回退正确性** | 人为占用设备 / 关闭系统独占许可，确认能回退且 UI 原因准确 |

> ⚠️ **沿用仓库既有约定**：真实音频设备的自动测试**必须零音量**；样本缺失要**显式跳过**，不能把模拟测试称为真实格式/设备验收。

## 九、一句话总结

**macOS 主线是「共享模式 + 可能重采样 + 明确不承诺 bit-perfect」，而 Windows 版用 WASAPI 独占可以把整数 PCM 按原生采样率、原生位深、零转换直接送到 DAC——在输出模式、采样率跟随、bit-perfect 三项上明确超过 macOS 主线。**

**唯一的诚实前提**：软件音量衰减与 bit-perfect 天然互斥，所以提供独立的「bit-perfect 模式」（锁定 unity gain），并在界面**如实显示当前实际输出格式与信号路径**，让效果可被验证，而不是只靠宣称。
